## ตั้งค่า Supabase (สำหรับเก็บ lead จริง)

คัดลอก `apps/web/.env.example` เป็น `apps/web/.env.local` แล้วใส่ค่า

```
NEXT_PUBLIC_SUPABASE_URL=...
SUPABASE_SERVICE_ROLE_KEY=...
```

ต้องใช้สองคีย์: **secret** (เดิมชื่อ service_role) สำหรับงานที่ข้าม RLS
และ **publishable** (เดิมชื่อ anon) สำหรับอ่านในนามผู้ใช้ให้ RLS บังคับสิทธิ์
secret key อยู่ฝั่ง server เท่านั้น ห้ามส่งไปฝั่ง browser

คีย์อยู่ที่ Dashboard > Project Settings > API Keys > secret (ขึ้นต้น `sb_secret_`)
ต้องกด reveal แล้วคัดลอกให้ครบ — คีย์ที่คัดลอกไม่ครบจะได้ 401 "Unregistered API key"

ยังไม่ตั้งค่า: โหมด dev จะเขียน lead ลง `apps/web/.leads.local.jsonl` แทน (กันข้อมูลหายระหว่างพัฒนา),
โหมด production จะตอบ 503 ไม่รับข้อมูลเงียบ ๆ

## ชั้นธุรกิจที่ 2 — Lead Marketplace (ทำแล้ว)

ผู้ติดตั้งสมัคร → ได้เครดิตทดลอง 3 เครดิต → เห็น lead ในตลาดแบบปกปิดข้อมูลติดต่อ →
ซื้อด้วยเครดิต → เห็นชื่อ/เบอร์จริง และเปิดรายงานฉบับเต็มของลูกค้ารายนั้นได้

ราคาตาม segment: บ้าน 1 เครดิต · SME 3 เครดิต · C&I 8 เครดิต (แก้ที่ `lib/pro.ts`)

### สองด่านที่กันข้อมูลช่างไม่ให้ปนกัน

**ด่านที่ 1 — token ไม่เคยถึงมือ JavaScript** เซสชันเก็บใน httpOnly cookie ฝั่ง server
ไม่ได้ใช้ `@supabase/ssr` ที่เก็บ token ไว้ในเบราว์เซอร์ (ยืนยันแล้วว่า `document.cookie` ว่าง
และไม่มี token โผล่ใน HTML/RSC payload ของ `/pro` และ `/pro/leads`)

**ด่านที่ 2 — RLS บังคับที่ฐานข้อมูล** ฝั่ง server เอา token ไปสร้างไคลเอนต์ในนามผู้ใช้ผ่าน
`supabaseAsUser()` (publishable key + JWT) การอ่านข้อมูลของช่างจึงถูก RLS คุมอีกชั้น
ถ้าโค้ดเผลอ query ของคนอื่นจะได้ค่าว่าง ไม่ใช่ข้อมูลจริง — พิสูจน์แล้วด้วยช่างสองบัญชี:
ต่างคนต่างเห็นเฉพาะโปรไฟล์ เครดิต การซื้อ และ lead ของตัวเอง ยิงถามของอีกฝ่ายตรง ๆ ได้ `[]`

`supabaseAdmin()` (secret key ข้าม RLS) เหลือใช้เฉพาะงานที่ไม่มีผู้ใช้ล็อกอินหรือจงใจต้องเห็นข้ามคน:
รับ lead จากคนทั่วไป · แสดงตลาดแบบปกปิด · เปิดรายงานผ่านลิงก์ของลูกค้า · สร้างบัญชีช่าง ·
นับจำนวน lead ในตลาด · เขียน `lead_purchases` (schema ไม่มีนโยบาย insert ให้ผู้ใช้)

⚠ `SessionUser` มี `accessToken` อยู่ด้วย — **ห้ามส่งทั้งก้อนเข้า client component**
เพราะจะถูก serialize ไปกับ RSC payload แล้ว token ไปโผล่ในเบราว์เซอร์
(`ProHeader` จึงรับแค่ `label` กับ `credits`)

### การซื้อ lead เป็น atomic แล้ว

ตรรกะทั้งหมดอยู่ใน `supabase/purchase_lead.sql` — เช็คสิทธิ์ · เช็คสถานะ lead · เช็คยอดเครดิต ·
เขียน `lead_purchases` และ `credit_transactions` อยู่ใน transaction เดียว

กุญแจคือ **ล็อกแถวโปรไฟล์ของช่างก่อนเช็คยอด** (`select ... from profiles where id = auth.uid() for update`)
การซื้อของช่างคนเดียวกันจึงเกิดทีละรายการ คำขอถัดไปอ่านยอดหลังหักแล้วเสมอ
แล้วล็อกแถว lead ต่ออีกชั้นกัน lead แบบ `exclusive` ถูกขายสองรอบ (ลำดับล็อก profiles → leads เสมอ ไม่มี deadkock)

ทดสอบแล้ว: ช่างมี 3 เครดิต ยิงซื้อ lead 5 ใบพร้อมกัน ใบละ 1 เครดิต → สำเร็จ 3 ใบพอดี
อีก 2 ใบได้ `insufficient_credits` ยอดจบที่ 0 ไม่ติดลบ และผลรวมสมุดบัญชีตรงกับจำนวนใบที่ซื้อ

ฟังก์ชันเป็น `security definer` (ต้องเขียน `lead_purchases` ที่ schema ไม่เปิด insert ให้ผู้ใช้)
แต่ยึด `auth.uid()` เอง ไม่รับ `installer_id` จากภายนอก และตั้ง `search_path = ''` กันการสลับ schema
สิทธิ์เรียกให้เฉพาะ `authenticated`

### เติมเครดิตด้วยการโอน + แนบสลิป

ช่างเลือกแพ็กเกจ → โอนเงิน → แนบสลิป → ระบบบันทึกเป็น `payments` สถานะ `pending`
**เครดิตยังไม่เข้า** จนกว่าแอดมินจะเปิดสลิปดูแล้วกดยืนยันที่ `/pro/admin`

- ราคาและจำนวนเครดิตคิดจาก `CREDIT_PACKAGES` ฝั่ง server เสมอ ฟอร์มส่งมาแค่รหัสแพ็กเกจ
- สลิปเก็บใน Supabase Storage bucket `slips` แบบ **private** แยกโฟลเดอร์ตาม installer
  เปิดดูได้เฉพาะผ่าน signed URL อายุ 10 นาทีที่หน้าแอดมินสร้างให้ — เปิด URL สาธารณะได้ 400
- ตรวจชนิดและขนาดไฟล์ซ้ำฝั่ง server (JPG/PNG/WEBP/PDF ไม่เกิน 5 MB) ไม่เชื่อ `accept` ของ input
- ถ้าเขียน `payments` ไม่สำเร็จ จะลบไฟล์สลิปทิ้ง ไม่ให้เหลือไฟล์กำพร้า
- ยืนยัน/ปฏิเสธเป็น atomic เช่นกัน (`confirm_payment` / `reject_payment`) กดสองครั้งเครดิตไม่เข้าซ้ำ

⚠ **ไฟล์ SQL ทุกไฟล์ต้องเป็น ASCII ล้วน** — เวอร์ชันที่มีคอมเมนต์ภาษาไทยรันใน SQL Editor
ไม่ผ่าน (`schema.sql` กับ `purchase_lead.sql` ที่ผ่านมาได้เป็นข้อยกเว้น) คำอธิบายภาษาไทย
ให้เขียนไว้ใน README แทน อย่าใส่กลับเข้าไปในไฟล์ .sql

บัญชีรับโอนตั้งผ่าน `NEXT_PUBLIC_PAYEE_*` ใน `.env.local` ไม่ hardcode เลขบัญชีไว้ในโค้ด
ถ้ายังไม่ตั้งค่า หน้าจะขึ้นคำเตือนและปิดปุ่มแจ้งโอนไว้

**การตั้งแอดมิน** ยังไม่มีหน้าจัดการ ต้องสั่งใน SQL Editor:
`update profiles set role = 'admin' where id = (select id from auth.users where email = 'you@example.com');`

### โหมดละเอียด — ปรับสมมติฐานเองได้ 18 ค่า

ไม่ได้แยกเป็นสองหน้า แต่กางอยู่บนหน้าเดิมใต้ฟอร์ม 6 ช่อง กดปุ่ม "ปรับสมมติฐานเอง" แล้วกางเป็น
5 กลุ่ม: อัตราค่าไฟ · เทคนิค · ต้นทุนและกำไร · แบตเตอรี่ · การเงิน

- ทุกช่องเติมค่ามาตรฐานไว้ให้แล้ว **ไม่มีช่องว่างให้ต้องกรอกใหม่** เปิด/ปิดโหมดไม่ล้างค่าที่กรอกไว้
- กลุ่มแบตเตอรี่โผล่เฉพาะตอนเปิด Hybrid · Load Factor โผล่เฉพาะประเภท 3 ที่คิดค่า Demand
- ช่องที่ถูกแก้จะไฮไลต์และมีปุ่ม "คืนค่า X" รายช่อง พร้อมป้ายนับรวมบนหัวข้อ
- จำนวนก้อนแบต 0 = ให้ระบบคำนวณให้พอดีโหลดกลางคืน ใส่ตัวเลขเอง = ใช้ตามนั้น
- ลิงก์รายงานพา**เฉพาะค่าที่ต่างจากมาตรฐาน**ไปด้วย ลิงก์จึงไม่ยาวเกินจำเป็น
- รายงานแสดงค่าที่ใช้คำนวณจริง (ไม่ใช่ค่ามาตรฐาน) พร้อมตารางแยกว่าปรับอะไรไปบ้าง

**ทุกค่าถูกบีบให้อยู่ในช่วงที่ยอมรับได้ทั้งฝั่ง client และ server** (`sanitizeAdvanced`)
ทดสอบแล้ว: ยิง `psh=999, wacc=-50, years=1000, margin=9999` พร้อมคีย์ปลอม
ได้ผลเป็น `psh=6.5, wacc=0, years=30, margin=100%` และคีย์ปลอมถูกทิ้ง
ทั้งในรายงานและใน `calc_snapshot` ที่บันทึกลงฐานข้อมูล

`Quote.assumptions` คือค่าที่ใช้คำนวณจริง — **ทุกหน้าต้องอ่านจากตรงนี้ ห้ามอ่าน `CALC_DEFAULTS`
ตรง ๆ** ไม่งั้นรายงานที่ปรับสมมติฐานจะโชว์ตัวเลขคนละชุดกับที่ใช้คำนวณ

### captcha ที่ฟอร์มขอรายงาน

ใช้ **Cloudflare Turnstile** เพราะฟรีไม่จำกัด ไม่ต้องให้ผู้ใช้เลือกรูปภาพในกรณีทั่วไป
และไม่ส่งข้อมูลผู้ใช้ให้ผู้ให้บริการโฆษณา — ฟอร์มขอใบเสนอราคาไวต่อ friction มาก
ถ้าใส่ captcha แบบต้องแก้ปริศนาทุกครั้ง lead จะหายมากกว่าที่กัน bot ได้

- ใช้ทั้งที่ฟอร์มขอรายงาน (`/api/leads`) และหน้าสมัครผู้ติดตั้ง (`/api/auth/signup`)
- **ไม่ใช้ที่หน้าเข้าสู่ระบบ** — กันด้วย rate limit (10 ครั้ง/15 นาที/IP) อยู่แล้ว
  และการบังคับ captcha ทุกครั้งที่ล็อกอินสร้าง friction ให้ช่างที่เข้าใช้งานทุกวัน
- ตรวจ**ก่อน** validate และก่อนแตะฐานข้อมูล — bot ไม่ทำให้เสีย CPU และไม่เกิดบัญชีขยะ
- `token` ใช้ได้ครั้งเดียว อายุ 5 นาที ถ้าส่งไม่ผ่านวิดเจ็ตจะ reset ขอใหม่ให้อัตโนมัติ
- **ยังไม่ตั้งค่าคีย์ = ข้ามการตรวจ** ฟอร์มยังใช้งานได้ปกติ (มี log เตือนฝั่ง server)
- ถ้าเรียก Cloudflare ไม่สำเร็จ (เน็ตล่ม/timeout 8 วิ) จะ**ปล่อยผ่าน** — ทิ้ง lead จริงเสียหายกว่า
  ปล่อย bot ผ่านบางตัว
- ถ้าเบราว์เซอร์โหลดสคริปต์ Turnstile ไม่ได้ (เน็ตองค์กรบล็อก) ฟอร์มยังกดส่งได้
  แล้วไปโดนปฏิเสธที่ server แทน — ไม่ใช่หน้าจอค้างที่กดอะไรไม่ได้เลย

ตั้งค่าที่ `.env.local` (สร้างคีย์ฟรีที่ dash.cloudflare.com > Turnstile > Add site):

```
NEXT_PUBLIC_TURNSTILE_SITE_KEY=...
TURNSTILE_SECRET_KEY=...
```

ตอนนี้ `.env.local` ใส่ **test key ทางการของ Cloudflare (ผ่านเสมอ)** ไว้สำหรับพัฒนา
**ต้องเปลี่ยนเป็นคีย์ของโดเมนจริงก่อนขึ้น production** ไม่งั้นเท่ากับไม่มี captcha
คีย์ทดสอบชุดอื่นที่ใช้ตรวจได้: `2x0000000000000000000000000000000AA` = ไม่ผ่านเสมอ

### ตรวจ lead ก่อนขึ้นตลาด

lead ที่ลูกค้าส่งเข้ามาบันทึกด้วย `status = 'new'` (เข้าคิวรอตรวจ) **ไม่ขึ้นตลาดเอง**
เปลี่ยนเป็น `listed` ได้ทางเดียวคือแอดมินกดอนุมัติผ่าน `review_lead()` ที่ `/pro/admin/leads`

ในคิวแต่ละใบแสดงข้อมูลติดต่อเต็ม ค่าไฟ หน่วย ขนาดที่เหมาะสม ปุ่มเปิดรายงานฉบับเต็ม
ช่องปรับราคาขายก่อนอนุมัติ และ **ธงเตือนเมื่อเบอร์นั้นเคยส่งเข้ามาแล้ว** (จับการส่งซ้ำและ bot
ที่หลุด captcha มาได้) ตีตกแล้วจะเป็น `invalid` ไม่ขึ้นตลาดตลอดไป

`review_lead()` เปลี่ยนสถานะได้เฉพาะ lead ที่ยังเป็น `new` — กดซ้ำหรือกดพร้อมกัน
จึงไม่ทำให้ lead ที่ขายไปแล้วกลับขึ้นตลาด และตาราง `leads` ไม่มีนโยบาย UPDATE ให้ผู้ใช้
การเปลี่ยนสถานะจึงผ่านฟังก์ชันนี้เท่านั้น

### แจ้งเตือนและส่งรายงานทาง LINE

⚠ **LINE Messaging API ส่งไฟล์ PDF ไม่ได้** ชนิดข้อความที่ส่งได้มีแค่ text / sticker / image /
video / audio / location / imagemap / template / flex — ไม่มีชนิดไฟล์แนบ
ระบบจึงส่ง **การ์ด Flex พร้อมปุ่มลิงก์ไปหน้ารายงาน** ผู้รับกดแล้วสั่งพิมพ์เป็น PDF เองได้จากหน้านั้น
ถ้าอยากได้ไฟล์แนบจริง ๆ ต้องส่งทางอีเมลแทน หรือ render รายงานเป็นรูปภาพแล้วส่งเป็น image

**สามเส้นทางที่ทำไว้**

1. lead ใหม่เข้าคิว → แจ้งแอดมินทุกคนที่ผูก LINE ไว้ พร้อมปุ่มไปหน้าคิวตรวจ
2. แอดมินอนุมัติ lead → แจ้งช่าง **เฉพาะจังหวัดเดียวกับ lead** พร้อมราคาเครดิต
   (ตลาด lead ใครติดต่อก่อนได้ก่อน ความเร็วจึงเป็นคุณค่าหลักของฟีเจอร์นี้)
3. ลูกค้าส่งรหัสในแชต → ระบบส่งการ์ดรายงานให้ทันที

**การผูกบัญชีใช้ token ที่เซ็นด้วย HMAC ไม่ใช่รหัสสุ่มที่ต้องเก็บในตาราง** — token พกไอดี
เป้าหมายและเวลาหมดอายุมาในตัว webhook ถอดออกมาใช้ได้เลย ปลอมไม่ได้เพราะไม่รู้ channel secret
จึงไม่ต้องเพิ่มคอลัมน์ ไม่ต้องมี index และไม่ต้องเขียนงานล้างรหัสหมดอายุ (อายุ 24 ชม.)

ทำไมต้องให้คัดลอกรหัสไปวางเอง: LINE ไม่ยอมให้ส่งข้อความหาใครก่อนที่เขาจะเพิ่มเพื่อน
และตอนเพิ่มเพื่อนก็ไม่มีทางรู้ว่าเป็นใคร รหัสนี้คือตัวเชื่อมระหว่างคนบนเว็บกับคนในแชต

ตั้งค่าใน `.env.local` (สร้าง Official Account + Messaging API channel ที่ developers.line.biz):

```
LINE_CHANNEL_ACCESS_TOKEN=...
LINE_CHANNEL_SECRET=...
NEXT_PUBLIC_LINE_ADD_FRIEND_URL=https://line.me/R/ti/p/@yourid
NEXT_PUBLIC_SITE_URL=https://โดเมนจริง
```

แล้วตั้ง Webhook URL ที่ LINE Developers Console เป็น `https://โดเมนจริง/api/line/webhook`
(ต้องเป็น https สาธารณะ LINE เรียก localhost ไม่ได้ — ตอนพัฒนาใช้ ngrok หรือ Cloudflare Tunnel)

`NEXT_PUBLIC_SITE_URL` สำคัญ เพราะลิงก์ในข้อความ LINE ต้องเป็น absolute URL เสมอ

### ส่งรายงานเป็นไฟล์ PDF ทางอีเมล

อีเมลเป็น**ช่องทางเดียวที่ส่งไฟล์ให้ลูกค้าได้จริง** (LINE แนบไฟล์ไม่ได้) ฟอร์มขอรายงานจึงมี
ช่องอีเมลเพิ่มมาแบบ**ไม่บังคับ** — กรอกแล้วได้ PDF แนบไปให้ ไม่กรอกก็ยังใช้งานได้ทุกอย่าง
(ตั้งใจไม่บังคับเพราะฟอร์มนี้ไวต่อ friction)

**PDF สร้างโดยเปิดหน้า `/report/[id]?pdf=1` ด้วย Chromium จริง** ไม่ได้ประกอบ PDF เอง
เหตุผล: หน้ารายงานมีกราฟ Chart.js ที่วาดลง canvas และมีฟอนต์ไทย ถ้าประกอบเองต้องวาดกราฟใหม่
และฝังฟอนต์เอง งานเยอะและผลต่างกัน วิธีนี้ทำให้ "สิ่งที่เห็นบนเว็บ = สิ่งที่ได้ในไฟล์" เสมอ

- ใช้ `playwright-core` ที่**ไม่ดาวน์โหลดเบราว์เซอร์ 300MB** แล้วชี้ไป Chrome/Edge ที่เครื่องมีอยู่
  หาอัตโนมัติบน Windows/Linux/macOS หรือกำหนดเองด้วย `CHROME_EXECUTABLE_PATH`
- โหมด `?pdf=1` **ปิดอนิเมชันกราฟ** และหน้าปักธง `data-report-ready` เมื่อวาดเสร็จ
  ตัวสร้าง PDF รอธงนี้แทนการหน่วงเวลาแบบเดา — หน้าช้าก็ยังได้ไฟล์ครบ
- ผลจริงที่วัดได้: **3 หน้า ~290 KB สร้างเสร็จใน 1.9 วินาที** กราฟครบทั้ง 3 ตัว
- ช่างที่ซื้อ lead แล้วดาวน์โหลด PDF ได้ที่ `/api/pro/leads/[id]/pdf`

**ส่งอีเมลได้สองทาง เลือกอัตโนมัติจาก env**: Resend (`RESEND_API_KEY`) หรือ SMTP (`SMTP_HOST`)
ไม่ตั้งค่าเลย = ไม่ส่งและ log เตือน ไม่ทำให้ระบบอื่นพัง

**การส่งทำเบื้องหลัง ไม่บล็อกการตอบกลับฟอร์ม** — สร้าง PDF ใช้เวลาหลายวินาที ถ้ารอผู้ใช้จะค้าง
⚠ ใช้ได้กับเซิร์ฟเวอร์ที่รันค้างไว้ (`next start`) บน serverless งานหลังส่ง response อาจถูกตัด
ต้องย้ายไป queue หรือใช้ `waitUntil` ของแพลตฟอร์มนั้น

### จำกัดอัตราด้วยตัวนับส่วนกลาง

ตัวนับในหน่วยความจำคุ้มได้แค่โปรเซสเดียว พออยู่หลัง load balancer หรือขึ้น serverless
แต่ละอินสแตนซ์จะมีตัวนับของตัวเอง **ขีดจำกัดจริงจึงกลายเป็น N เท่าของที่ตั้งไว้**

ตอนนี้นับรวมกันในตาราง `rate_limits` ผ่าน `check_rate_limit()` — หนึ่งคีย์คือหนึ่งแถว
เก็บเวลาที่ยิงเป็น array แล้วตัดของเก่าทิ้งทุกครั้ง array จึงไม่โตเกินขีดจำกัด (ราว 20 ตัว)
`select ... for update` ทำให้คำขอที่ยิงพร้อมกันด้วยคีย์เดียวกันถูกนับทีละอัน

**ไม่ใช้ Redis** เพราะโปรเจกต์นี้มี Postgres อยู่แล้ว การเพิ่มบริการใหม่หมายถึงคีย์ใหม่
ค่าใช้จ่ายใหม่ และจุดที่พังได้อีกจุด ที่ปริมาณระดับนี้ Postgres เร็วพอ

**ถ้าเรียกฐานข้อมูลไม่สำเร็จจะถอยไปใช้ตัวนับในหน่วยความจำ ไม่ใช่ปล่อยผ่านทั้งหมด** —
ฐานข้อมูลสะดุดไม่ควรทำให้ระบบเปิดโล่ง และไม่ควรทำให้ลูกค้าจริงส่งฟอร์มไม่ได้

### แก้อัตราค่าไฟ กฟภ. รายโครงการ

ประกาศอัตราใหม่ออกมาก่อนที่เราจะอัปเดตค่ากลางเสมอ ช่างที่กำลังเสนอราคาต้องใช้อัตราที่
บังคับใช้จริงวันนั้น ไม่ใช่รอเรา deploy — ตรงกับหลักที่ล็อกไว้ตั้งแต่เฟส 0 ว่า
"อัตราค่าไฟแก้ที่ `pea-rates.ts` ที่เดียว override รายผู้ใช้ผ่าน `mergeRates()`"

- แสดงเฉพาะอัตราของประเภทผู้ใช้ไฟที่โครงการนั้นเลือก (ประเภท 3 = 3 ช่อง · ประเภท 1 = 12 ช่อง)
  ถ้าโชว์ทั้ง 8 ประเภทจะกลายเป็นฟอร์มร้อยช่อง
- **ช่วงหน่วยของแต่ละขั้นคงเดิม แก้ได้เฉพาะอัตรา** — ช่วงหน่วยเปลี่ยนน้อยกว่ามาก
  และการให้แก้ทั้งคู่จะเพิ่มโอกาสกรอกจนขั้นบันไดไม่ต่อเนื่อง
- อัตราที่แก้มีผลเฉพาะโครงการนั้น เก็บใน `projects.rate_override` และติดไปกับ snapshot
- รายงานขึ้นตารางแยกว่า "อัตราค่าไฟที่แก้จากประกาศมาตรฐาน N รายการ — ผู้จัดทำรายงานระบุอัตราเอง"
  ลูกค้าที่รับรายงานจะได้รู้ว่าตัวเลขไหนไม่ใช่อัตราประกาศ

⚠ **ฟอร์มสาธารณะแก้อัตราไม่ได้เด็ดขาด** — `validateQuoteInput()` ไม่แตะฟิลด์นี้เลย
เส้นทางของโปรเจกต์เท่านั้นที่รับ ทดสอบแล้ว: ยิง `rateOverride` เข้า `/api/leads` ถูกตัดทิ้ง
หน่วยที่คำนวณได้ยังเป็นอัตรามาตรฐาน ไม่งั้นใครก็สร้างรายงานอ้างอัตรามั่ว ๆ ไปหลอกคนอื่นได้

### เตือนก่อนแพ็กเกจหมดอายุทาง LINE

เดิมช่างจะรู้ว่าหมดอายุตอนกดสร้างโปรเจกต์ไม่ได้แล้ว ซึ่งสายเกินไป — เขาอาจกำลังคุยกับลูกค้าอยู่
การเตือนล่วงหน้าจึงทั้งกันรายได้รั่วและกันประสบการณ์แย่ในจังหวะที่สำคัญที่สุดของช่าง

- เตือนเมื่อเหลือ **7 · 3 · 1 · 0 วัน** (0 = วันที่หมดอายุพอดี) เป็นการ์ด LINE พร้อมปุ่มไปหน้าต่ออายุ
- **กันส่งซ้ำโดยใช้ตาราง `rate_limits` ที่มีอยู่แล้ว** ไม่ต้องเพิ่มคอลัมน์หรือตารางใหม่ — คีย์คือ
  `subrem:<installer_id>:<วันที่เหลือ>` ซึ่งเปลี่ยนวันละครั้ง ดังนั้นหนึ่งช่วงเตือน = ส่งครั้งเดียว
  ต่อให้ตั้งให้รันทุกชั่วโมงก็ตาม
- **ส่งไม่สำเร็จจะคืนตัวจำ** ให้รอบถัดไปลองใหม่ ไม่งั้น LINE ล่มชั่วคราวจะทำให้การเตือนรอบนั้น
  หายถาวรทั้งที่ควรได้ลองใหม่ (ตัวจำยังกันสองรอบที่รันพร้อมกันส่งซ้ำเหมือนเดิม)
- ช่างที่ยังไม่ได้ผูก LINE จะถูกข้ามพร้อมบอกเหตุผล ไม่นับเป็นล้มเหลว

เรียกด้วย `GET`/`POST` ที่ `/api/cron/subscription-reminders` แนบรหัสลับมาทาง
`Authorization: Bearer <CRON_SECRET>` หรือ `?key=<CRON_SECRET>` เทียบแบบ timing-safe
เติม `?dryRun=1` เพื่อดูว่าจะส่งหาใครบ้างโดยไม่ส่งจริง

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://<โดเมน>/api/cron/subscription-reminders
```

⚠ **ไม่ตั้ง `CRON_SECRET` = endpoint ปิดตาย** (คืน 401 เสมอ) ตั้งใจให้พลาดแล้วปิด ไม่ใช่พลาดแล้วเปิด
และ **ต้องมีตัวตั้งเวลาข้างนอกเรียกให้วันละครั้ง** — Vercel Cron, cron-job.org หรือ Task Scheduler
ตัวแอปไม่มีตัวจับเวลาในตัว

ทดสอบแล้ว: ไม่แนบรหัส/รหัสผิด → 401 · ตั้งวันหมดอายุให้ตรงทั้ง 4 ช่วง → จับครบทั้ง 4 ·
คนที่ไม่ได้ผูก LINE → ข้ามพร้อมเหตุผล · รันซ้ำรอบสอง → ข้ามทั้งหมด ไม่ส่งซ้ำ

## นำขึ้นใช้งานจริง (deploy)

**เลือก host ที่รัน container ได้** — Railway, Fly.io หรือ VPS ไม่ใช่ serverless
เพราะการสร้าง PDF เปิด Chromium จริงแล้วรอกราฟวาดเสร็จ ใช้เวลาหลายวินาทีและกินแรมหลายร้อย MB
ซึ่งชนเพดานเวลาของ serverless พอดี และ PDF ไม่ใช่ของเสริม — การส่งรายงานทางอีเมลสร้างบนตัวนี้ทั้งหมด

`Dockerfile` ที่รากโปรเจกต์พร้อมใช้แล้ว สร้างภาพ 3 ชั้น (ติดตั้ง dependency → build → รัน)

### ⚠ ค่า NEXT_PUBLIC_* ต้องส่งตอน build ไม่ใช่ตอนรัน

Next ฝังค่าพวกนี้ลงในโค้ดตอน build ถ้าตั้งตอนรันอย่างเดียวจะไม่มีผล

```
NEXT_PUBLIC_SITE_URL          NEXT_PUBLIC_SUPABASE_URL      NEXT_PUBLIC_SUPABASE_ANON_KEY
NEXT_PUBLIC_TURNSTILE_SITE_KEY  NEXT_PUBLIC_LINE_ADD_FRIEND_URL

```

**เปลี่ยนโดเมนเมื่อไหร่ = ต้อง build ใหม่** ค่าที่เหลือ (คีย์ลับทั้งหมด) อ่านตอนรันตามปกติ
ตั้งเป็น environment variable ของ service ได้เลย ดูรายการครบใน `apps/web/.env.example`

### ตามลำดับ

1. push ขึ้น GitHub เป็น **private repo** — README เขียนสถาปัตยกรรมความปลอดภัยไว้ละเอียด
2. สร้าง service จาก repo ให้ build ด้วย `Dockerfile`
3. ใส่ตัวแปรทั้งหมดจาก `.env.example` โดยเฉพาะ `SUPABASE_SERVICE_ROLE_KEY` และ `CRON_SECRET`
   (**สุ่มใหม่ ห้ามใช้ค่าทดสอบในเครื่อง**)
4. deploy แล้วเอาโดเมนที่ได้มาตั้งเป็น `NEXT_PUBLIC_SITE_URL` แล้ว **build ใหม่อีกครั้ง**
   รอบแรกยังไม่รู้โดเมนของตัวเอง
5. ชี้ปลายทางให้ตรงโดเมนจริง — LINE webhook, Supabase redirect URL, โดเมนของ Turnstile
6. ตั้งตัวตั้งเวลาข้างนอกให้เรียก `/api/cron/subscription-reminders` วันละครั้ง

### ที่ทดสอบแล้วกับที่ยังไม่ได้ทดสอบ

ทดสอบแล้วบนเครื่อง: `output: 'standalone'` build ผ่านทั้งที่เอนจินอยู่นอก `apps/web` ·
รันเซิร์ฟเวอร์ standalone แล้วหน้าเว็บ ไฟล์ static โลโก้ และ endpoint cron ทำงานครบ ·
สร้าง PDF จาก playwright-core ที่อยู่ใน standalone ได้จริง

**ยังไม่ได้ทดสอบ: การ build ภาพ Docker จริง** (เครื่องที่พัฒนาไม่มี Docker)
สิ่งที่ควรตรวจรอบแรกที่ deploy คือ **ภาษาไทยใน PDF ไม่กลายเป็นกล่องสี่เหลี่ยม**

### กับดักที่เจอมาแล้ว

`playwright-core` เรียก `browsers.json` แบบไดนามิก ตัว trace ของ Next จึงมองไม่เห็นและไม่ก๊อปมาให้
**build ผ่านแต่ PDF พังตอนรันจริง** แก้ด้วย `outputFileTracingIncludes` ใน `next.config.ts`
ถ้าอัปเกรด playwright แล้ว PDF พังขึ้นมาเฉย ๆ ให้ดูตรงนี้ก่อน
